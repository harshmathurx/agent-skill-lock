# Examples

The examples are tiny on purpose. Each one is a fake repository with real agent surfaces and a real `agent-skills.lock.json` generated by this CLI.

Use them to see the product loop:

```bash
pnpm build
node dist/cli.js check --root examples/claude-mcp-webapp
node dist/cli.js diff --root examples/claude-mcp-webapp
```

If you edit an agent file inside an example, `check` should fail until you run:

```bash
node dist/cli.js update --root examples/claude-mcp-webapp
```

## Example repos

### `claude-mcp-webapp`

A small web app repo that uses Claude Code for issue triage and browser checks. It has:

- `CLAUDE.md` with repo rules
- `.claude/skills/release-check.md`
- `.claude/mcp.json` with filesystem and Playwright MCP servers

The lockfile shows two important things: a filesystem server scoped to `.`, and browser/network capability through Playwright.

Review story: if someone adds a new MCP server or changes the release skill to publish automatically, the lockfile changes.

### `codex-data-worker`

A data-worker repo with Codex instructions and a Postgres MCP server. It has:

- `AGENTS.md`
- `.codex/instructions.md`
- `.mcp.json`

The MCP config references `DATABASE_URL` and `READONLY_REPORTING_TOKEN`. The lockfile records the names, not the values.

Review story: a PR that changes a readonly data agent into a mutating one should not look like an ordinary docs edit.

### `cursor-hermes-plugin`

A plugin repo where Cursor rules and a Hermes skill both matter. It has:

- `.cursorrules`
- `.cursor/mcp.json`
- `.hermes/skills/release-notes/SKILL.md`

The Hermes skill advertises required commands and env vars through frontmatter. The lockfile captures those as capabilities.

Review story: publishing language in a release skill triggers a public side-effect hint.

### `mixed-agent-monorepo`

A team repo with several agent surfaces in one place. It has:

- `AGENTS.md`
- `CLAUDE.md`
- `.cursor/rules/frontend.mdc`
- `.hermes/skills/deploy/SKILL.md`
- `mcp.json`

This is the example closest to a real messy repo. Multiple agent tools can change behavior through different files. One lockfile gives the reviewer a single place to inspect the surface.

## What to look for in a diff

A good lockfile diff answers:

- Did a new MCP server appear?
- Did a command change from readonly to mutating?
- Did the repo add a secret-looking environment variable name?
- Did an instruction file start allowing deploy, merge, publish, or comment behavior?
- Did an agent gain filesystem scope over the repo or home directory?

The tool does not know whether a change is acceptable. It makes the change harder to miss.
